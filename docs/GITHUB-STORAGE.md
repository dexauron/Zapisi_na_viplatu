# Перенос «Сверки» на GitHub — промежуточное состояние

**Рабочая программа НЕ переключена.** Ветка `codex/github-storage-20261123` содержит экспериментальный полный путь одной команды на вымышленных данных: подпись → проверка прав → существующий PostgreSQL → шифрованный снимок и персональные наборы → один git-коммит → зашифрованный ответ. Действующие вход, база, Pages и каталог не изменены.

## Что сделано

- `assets/github/protocol.js`: браузер и Node, ECDSA P-256, привязка к магазину, пользователю, эпохе ключа и UUID команды; проверка срока; запрос в гибридном RSA-OAEP-3072/AES-256-GCM конверте. ФИО, сумма и действие не находятся в открытом Issue.
- `assets/github/queue.js`: перед отправкой сохраняет только зашифрованный запрос и контрольный хеш; повтор использует тот же UUID и конверт. Отправка даёт `pending`, только проверенный персональный ответ — `confirmed` либо `rejected`. После 25 часов без результата — `needs_review`, без автоматического подтверждения или отмены выплаты. В HTML пока не подключён.
- `scripts/github/postgres.cjs`: разрешённые RPC и операции таблиц, параметры и типы из схемы, связанная SQL-подстановка. Личность и актуальная роль берутся из доверенного профиля и самой базы. Штатные RLS, триггеры и `set_payout_paid` сохраняют авторство, блокировку, ожидаемую версию и запрет прямой смены выдачи. Массовые UPDATE/DELETE без ID не принимаются. Учётки `staff-admin` этим адаптером ещё не заменены.
- `scripts/github/snapshot.cjs`: согласованный снимок 11 таблиц public, `private.shared_link`, `private.import_seen`, минимальной метаинформации `auth.users` и счётчика аудита. Строки сохраняются текстом JSON PostgreSQL: десятичные суммы и микросекунды не проходят через JS Date/Number. Шестнадцать постоянных блоков на таблицу; неизменённые блоки не перешифровываются, пустые не загружаются. Gzip перед шифрованием, HMAC для сравнения содержимого, ограничение размера. Восстановление требует специальной пометки временной базы и завершается побайтовой сверкой строк.
- `scripts/github/views.cjs`: персональные наборы чтения, полученные под фактической ролью PostgreSQL. Сотруднику не выдаются финансовые таблицы; торговому — только его штатный кабинет. Смена ссылки формирует закрытый набор с отметкой отзыва. У каждого пользователя свой ключ. Изменяются только затронутые блоки.
- `scripts/github/processor.cjs` и `engine.cjs`: проверка подписи и доступа, идемпотентность по пользователю/UUID/хешу; эффект, журнал, персональные наборы и ответ фиксируются одним коммитом. Отказ SQL также сохраняется как отказ. При конфликте старый снимок не переносится на новую вершину; при потерянном ответе последующий запуск читает журнал принятого коммита. Временная SQL-транзакция всегда откатывается.
- `scripts/github/inbox.cjs` и `github.cjs`: чтение долговечной очереди из открытых Issues, привязка файлов к одному точному коммиту, обход страниц до закрытия задач, отсутствие токена в URL и запрет редиректов. В публичном логе только счётчики и обезличенные коды. Непонятный исход Git не закрывает команду.
- `assets/github/store.cjs`: парольные конверты PBKDF2-SHA256/600000 и отдельные конверты случайного ключа; строгие разрешённые пути/поля, публикация через Git Data API без force push.
- `.github/workflows/github-storage.yml`: подготовлен запуск обработчика на одноразовом локальном PostgreSQL с нашими миграциями. **Отключён**, пока `SVERKA_GITHUB_STORAGE_ENABLED` не равна `true`. Не принимает адрес рабочей БД. Не переключает UI. Установки, секреты и ветка данных ещё не создавались.

## Проверено локальным запуском

На вымышленных данных: 84 модульных теста, 38 проверок DOM выплат и 28 поиска; чистый PostgreSQL 18.6 — 22 миграции, 145 прежних SQL-сценариев, 5 проверок двух соединений и 57 новых проверок адаптера/снимка/персональных наборов/сквозной команды. CI расширен этим сценарием на штатном PostgreSQL 17 Supabase; первый удалённый CI выявил отдельные права служебных счётчиков Auth; отказ устранён без их сброса. Повторный CI для опубликованного коммита `69383e2` прошёл все 4 задания, включая 57 сквозных проверок на PostgreSQL 17. Последующее обновление документации не меняет проверенный код.

Проверены: все используемые RPC адаптера, импорт JSON/массивов 1С, РКО → **«Деньги отложены»** без `paid_at`/`paid_by`, видимость старого резерва торговому и в общем графике, запрет подтверждения резерва торговым; права сотрудника и чужой токен; сохранность точных версий после восстановления; отказ/повтор/конфликт/потерянный ответ Git; шифрование ответа только инициатору; состав персональных наборов и отзыв ссылки. ## Что остаётся до переключения

1. Вход по логину/паролю, безопасная выдача и смена индивидуальных ключей, операции создания/блокировки/удаления сотрудников и учёток ТП. Пароли Supabase **не переносятся**: в снимке нет хешей паролей, факторов, сессий и иных данных Auth. Этот снимок не является полным резервом Supabase Auth.
2. Читающий провайдер для персональных наборов: быстрый поиск и сводки без запуска Actions, проверка версии/эпохи, шифрованный кэш. Затем подключение провайдера и очереди к действующим экранам, явные подписи ожидания/отказа и ручная проверка неопределённого результата.
3. Большие загрузки 1С: одно Issue ограничено 60 000 символов нашим клиентом. Нужен отдельный проверенный транспорт пачек/вложений; обход ограничения выдачей сотрудникам ключа записи кода запрещён.
4. Инициализация ветки `github-data`, согласованный перенос реальных данных с точным сопоставлением сумм, авторов, времени, документов и учёток; проверка ссылок и обратимого переключения. Без этого рабочую базу нельзя выключать.
5. Нагрузочная проверка на фактическом размере магазина: API-запросы, объём/рост git-истории, стоимость запусков и задержки при 15 сотрудниках и примерно 600 ТП. Текущий REST-прототип ограничивает один коммит 1000 изменёнными файлами; первичная публикация и массовое обновление должны уложиться в этот предел и лимиты GitHub. При необходимости заменить транспорт пачкой git-объектов, не ослабляя CAS и атомарность.
6. Проверка прав и задержек в настоящем Actions, восстановление после обрыва, срок жизни/отзыв узкого Issues-токена и ключей; проверка на российских сетях с VPN и без него.

## Настройки для будущего стенда — пока не включать

Ветка данных `github-data` должна заранее содержать **согласованный** зашифрованный `data/v1/state.enc` и его блоки. Включение без снимка завершается ошибкой, пустую базу автоматически не создаёт. `schemaHash` вычисляется по именам и точному содержимому миграций; несовпадение блокирует восстановление до явной миграции состояния.

Secrets Actions: `SVERKA_STATE_KEY` — случайные 32 байта в base64; `SVERKA_BROKER_PRIVATE_KEY` — закрытый RSA JWK. Variables: `SVERKA_STORE`, затем `SVERKA_GITHUB_STORAGE_ENABLED=true` **только для готового стенда**. Закрытые ключи/пароли нельзя публиковать в Issue, коммитах, скриншотах или чате. Сотрудникам нужен лишь узкий токен Issues без Contents/Actions/Administration; владелец должен отдельно настроить и проверить этот доступ. Общий Issues-токен остаётся риском для доступности очереди при утечке; подпись не даёт превратить его в право выдачи денег.

Постоянного Supabase в целевом режиме нет: его CLI запускает только временный PostgreSQL в Actions, с теми же локальными миграциями и функциями Auth/RLS. На этом этапе код не обещает гарантированно бесплатную бессрочную работу, определённое время записи или доступность GitHub из всех российских сетей.

## Ограничения самой очереди GitHub

Команда хранится в Issue, поскольку стандартная группа concurrency может заменить ожидающий запуск, а расписание может задержаться или потерять запуск. Запасной запуск запланирован четыре раза в час; он также не гарантирует срок выполнения. В публичном репозитории расписания могут отключаться после 60 дней без активности. Источники: [concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [события](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [отключение workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).
